# AMACI on Starknet: zkSTARK-Based Anonymous Voting

## Overview

This document describes the architecture and implementation of AMACI (Anonymous Minimal Anti-Collusion Infrastructure) on Starknet, using zkSTARK proofs generated by Cairo programs. The system enables private, anti-collusion voting where vote privacy is preserved through encryption and correctness is guaranteed by zero-knowledge proofs — without requiring a trusted setup.

---

## Glossary

Key terms used throughout this document:

| Term | Explanation |
| --- | --- |
| **felt252** | Cairo's fundamental data type, short for "field element" (252-bit). It is an element of the STARK prime field (P = 2^251 + 17×2^192 + 1), with values ranging from 0 to P-1. All Cairo program inputs and outputs are ultimately represented as felt252 arrays. |
| **Cairo** | A programming language developed by StarkWare, designed specifically for generating STARK proofs. Every step of program execution is recorded as an "execution trace", from which the prover generates a zero-knowledge proof. |
| **Sierra** | The compiled intermediate form of a Cairo program (Safe Intermediate Representation). `.cairo` source code is compiled via `scarb build` into a Sierra JSON file — this file is the "circuit" submitted to the prover. |
| **Witness** | Private data held by the prover (Operator), such as the coordinator's private key, decrypted vote commands, and Merkle paths. This data never appears in the public output, but the proof guarantees its correctness. |
| **Commitment** | A hash binding to a value, typically `H(value, salt)`. Only the commitment is stored on-chain, not the original value. No one can reverse a commitment to recover the original value, but anyone can verify whether a given value matches a commitment. |
| **Fact** | A record registered in Starknet's Integrity FactRegistry, attesting that "a specific Cairo program executed correctly on a given input and produced a specific public output." On-chain contracts query facts to verify proofs. |
| **Poseidon** | A hash function designed specifically for finite field arithmetic. It is extremely efficient in STARK proofs because its internal structure consists entirely of field additions and multiplications. All Merkle trees, commitments, and input hashes in this system use Poseidon. |
| **Operator** | The entity running the AMACI round. Responsible for collecting encrypted votes, decrypting and processing them, generating proofs, and submitting to the chain. The Operator can see vote plaintext but cannot tamper with results (constrained by ZK proofs). |
| **Atlantic** | A Proving-as-a-Service platform by Herodotus. The Operator submits programFile + inputFile; Atlantic executes the program, generates a STARK proof, verifies it on Starknet, and registers the resulting fact. |

### Cairo Program Compilation and Execution

```text
Compilation (one-time):
  .cairo source ──scarb build──→ Sierra JSON (programFile)
  
  Sierra JSON is the compiled program representation, analogous to
  Java's .class files or WebAssembly. It defines all constraint logic
  and does not change once compiled.

Execution and proving (different each round):
  Sierra JSON + felt252[] (inputFile) ──→ execution trace ──→ STARK proof
  
  The inputFile is business data prepared by the Operator, serialized
  as a felt252 array following the Cairo struct field order. Different
  voting rounds produce different inputFiles.
```

## Part 1: aMACI Cairo Circuit Architecture

### What Are the Cairo Circuits?

In this system, "circuits" are Cairo programs that verify AMACI state transitions. Each program takes private witness data as input, performs cryptographic verification, and outputs a set of public commitments. Programs are compiled via `scarb build` into Sierra JSON, and a STARK prover generates a proof from the program's execution trace.

```text
┌──────────────────────────────────────────────────────────────┐
│                    Cairo Program (Circuit)                   │
│                                                              │
│  Input:   public fields + private witness (felt252 array)    │
│  Logic:   cryptographic verification (Poseidon hash,         │
│           Merkle path, signature check, state transition)    │
│  Output:  canonical public output (Array<felt252>)           │
│                                                              │
│  The STARK proof guarantees:                                 │
│  "There exists a valid witness such that the program         │
│   executed correctly and produced this public output."       │
└──────────────────────────────────────────────────────────────┘
```

### Circuit Parameters (2-1-1-3)

The current implementation uses a fixed parameter set:

| Parameter | Value | Meaning |
| --- | ---: | --- |
| stateTreeDepth | 2 | 5-ary Merkle tree, 25 state leaves |
| intStateTreeDepth | 1 | 5 leaves per tally batch |
| voteOptionTreeDepth | 1 | 5 vote options per voter |
| messageBatchSize | 3 | 3 encrypted messages per proof batch |

### Circuit Family

The system consists of four circuit families, each responsible for one phase of the AMACI round:

```text
┌─────────────────┐   ┌──────────────────────┐   ┌──────────────────────┐   ┌─────────────┐
│  Add New Key    │   │  Process Deactivate  │   │  Process Messages    │   │    Tally    │
│                 │   │                      │   │                      │   │             │
│  Proves key     │   │  Proves 3 deactivate │   │  Proves 3 vote       │   │  Proves     │
│  registration   │   │  requests are valid  │   │  commands are valid  │   │  vote count │
│  is well-formed │   │  and state updated   │   │  and state updated   │   │  is correct │
└─────────────────┘   └──────────────────────┘   └──────────────────────┘   └─────────────┘
```

#### 1. Add New Key (`add_new_key_native`)

Proves that a voter's key rotation is legitimate. This circuit has no Stage/Boundary/StepCore split because the logic is simple enough to fit in a single function.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                     Add New Key (single circuit, single proof)                │
│                                                                             │
│  Input (witness):                                                           │
│    coordPubKey          Coordinator public key                              │
│    oldPrivateKey        Old private key being rotated out                   │
│    newPubKey            New public key being registered                     │
│    pollId              Poll identifier                                      │
│    c1, c2              ElGamal ciphertext from deactivation leaf            │
│    d1, d2              Re-randomized ciphertext                             │
│    sharedKey           ECDH shared key                                      │
│    deactivateIndex     Leaf index in deactivation tree                      │
│    deactivateLeafPath[0..3]  4-level Merkle path                            │
│                                                                             │
│  Verification steps:                                                        │
│                                                                             │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 1. Hash binding verification                                         │   │
│  │    • H(coordPubKey) == coordPubKeyHash                               │   │
│  │    • H(newPubKey) == newPubKeyHash                                   │   │
│  │    • H(c1) == c1Hash, H(c2) == c2Hash                               │   │
│  │    • H(sharedKey) == sharedKeyHash                                   │   │
│  │    • H(d1) == d1Hash, H(d2) == d2Hash                               │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                         │                                                    │
│                         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 2. Nullifier computation                                             │   │
│  │    nullifier = Poseidon(domain, oldPrivateKey, pollId)                │   │
│  │    → Prevents the same old key from registering a new key twice      │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                         │                                                    │
│                         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 3. Deactivation leaf verification                                    │   │
│  │    deactivateLeaf = Poseidon(domain, c1Hash, c2Hash, sharedKeyHash)  │   │
│  │    → Proves the old key was actually deactivated (leaf data correct) │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                         │                                                    │
│                         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 4. Merkle inclusion proof                                            │   │
│  │    Rebuild tree root from deactivateLeaf + path[0..3]                │   │
│  │    assert(rebuilt root == deactivateRootHash)                         │   │
│  │    → Proves this deactivation leaf exists in the deactivation tree   │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                         │                                                    │
│                         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 5. Re-randomization binding                                          │   │
│  │    rerandomizeBindingHash =                                          │   │
│  │      Poseidon(domain, coordPubKeyHash, c1Hash, c2Hash, d1Hash, d2Hash)│  │
│  │    → Proves d1/d2 is a valid re-randomization of c1/c2              │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                         │                                                    │
│                         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 6. Input Hash (serves the same role as Boundary)                     │   │
│  │    inputHash = Poseidon(domain, deactivateRoot, coordPubKeyHash,     │   │
│  │                nullifier, c1Hash, c2Hash, sharedKeyHash,             │   │
│  │                deactivateLeafHash, d1Hash, d2Hash,                   │   │
│  │                rerandomizeBindingHash, newPubKeyHash, pollId)         │   │
│  │    → Aggregates all public fields into one hash for on-chain check   │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  Public output (19 felts):                                                  │
│    magic, version, circuitId, hashScheme,                                   │
│    stateTreeDepth, deactivateTreeDepth,                                     │
│    deactivateRootHash, coordPubKeyHash, nullifier,                          │
│    c1Hash, c2Hash, sharedKeyHash, deactivateLeafHash,                       │
│    d1Hash, d2Hash, rerandomizeBindingHash,                                  │
│    newPubKeyHash, pollId, inputHash                                         │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Why doesn't Add New Key need the Stage/Boundary/StepCore split?**

- It processes a single operation (not a batch), so there is no "chain multiple messages together" requirement
- There is no state root chain (it only reads the deactivation tree, does not update the state tree)
- The logic is small enough to express clearly in one function

#### 2. Process Deactivate (`process_deactivate_stage_native`)

Proves that a batch of 3 deactivation messages was processed correctly. For each message, the circuit verifies:

- **ECDH**: the coordinator's shared key is correctly derived
- **Decrypt**: the encrypted command decrypts to a valid deactivation request
- **Signature**: the voter's EdDSA signature authorizes the deactivation
- **State transition**: the active-state tree and deactivation tree are updated correctly

**Public output**: current/new deactivation commitments, message hash chain, state root.

#### 3. Process Messages (`process_messages_stage_native`)

Proves that a batch of 3 vote messages was processed correctly. For each message:

- **ECDH**: shared key derivation between voter and coordinator
- **Decrypt**: message decryption yields a valid vote command
- **Signature**: EdDSA signature verification
- **State transition**: vote weight, balance, and nonce updates are correct

**Public output**: current/new state commitments, deactivation commitment, message hash chain.

#### 4. Tally (`tally_votes_native`)

Proves that the final vote count is computed correctly from the processed state. Like Add New Key, this is a single-function circuit with no Stage/StepCore split.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                        Tally (single circuit, single proof)                   │
│                                                                             │
│  Input (witness):                                                           │
│    stateRoot            Final state root (from Process Messages output)     │
│    stateSalt            Salt for state commitment                           │
│    numSignUps           Number of registered voters                         │
│    batchNum             Which batch of 5 voters to tally (0..4)             │
│    stateLeaf[5][10]     5 state leaves in this batch                        │
│    statePathElements    Merkle path for this batch in the state tree        │
│    votes[5][5]          Vote weights: 5 voters × 5 options                  │
│    currentResults[5]    Accumulated results from previous batches           │
│    currentResultsRootSalt / newResultsRootSalt                              │
│                                                                             │
│  Verification steps:                                                        │
│                                                                             │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 1. State tree inclusion proof                                        │   │
│  │    • Hash each stateLeaf[i] → stateLeafHash[i]                      │   │
│  │    • Compute subroot = H(stateLeafHash[0..4])                        │   │
│  │    • Rebuild stateRoot from subroot + pathElements + batchNum         │   │
│  │    • assert(rebuilt root == witness.stateRoot)                        │   │
│  │    → Proves these 5 state leaves are actually in the state tree      │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                         │                                                    │
│                         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 2. State commitment                                                  │   │
│  │    stateCommitment = H(stateRoot, stateSalt)                         │   │
│  │    → Links this proof to the Process Messages output                 │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                         │                                                    │
│                         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 3. Vote root verification                                            │   │
│  │    For each voter i:                                                 │   │
│  │      voteRoot[i] = H(votes[i][0..4])                                │   │
│  │      assert(voteRoot[i] == stateLeaf[i].voteRootField)              │   │
│  │    → Proves the vote weights match what's stored in the state leaf   │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                         │                                                    │
│                         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 4. Current tally commitment check                                    │   │
│  │    If first batch (batchNum == 0):                                   │   │
│  │      assert(currentTallyCommitment == 0)                             │   │
│  │    Else:                                                             │   │
│  │      currentTallyCommitment = H(H(currentResults), currentSalt)      │   │
│  │    → Ensures continuity with previous tally batches                  │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                         │                                                    │
│                         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 5. Tally computation (quadratic voting)                              │   │
│  │    For each option j:                                                │   │
│  │      newResults[j] = currentResults[j]                               │   │
│  │                     + Σ tallyVote(votes[i][j]) for i in 0..4         │   │
│  │    where tallyVote(v) = v × (v + MAX_VOTES)                         │   │
│  │    → Accumulates vote weights using quadratic cost formula           │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                         │                                                    │
│                         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 6. New tally commitment                                              │   │
│  │    newTallyCommitment = H(H(newResults), newResultsRootSalt)         │   │
│  │    → This is what gets stored on-chain                               │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                         │                                                    │
│                         ▼                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │ 7. Input Hash                                                        │   │
│  │    inputHash = Poseidon(domain, packedVals, stateCommitment,         │   │
│  │                         currentTallyCommitment, newTallyCommitment)  │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  Public output (12 felts):                                                  │
│    magic, version, circuitId, hashScheme,                                   │
│    stateTreeDepth, intStateTreeDepth, voteOptionTreeDepth,                  │
│    packedVals, stateCommitment,                                             │
│    currentTallyCommitment, newTallyCommitment, inputHash                    │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Key design points:**

- The tally processes voters in batches of 5 (determined by `intStateTreeDepth = 1`, so 5^1 = 5 per batch). With 2-1-1-3 parameters and 1 signup, only batch 0 is needed.
- `stateCommitment` in the tally output must equal `newStateCommitment` from Process Messages — this is how the commitment chain links the two stages.
- The actual vote totals (plaintext) are never stored on-chain. Only the `newTallyCommitment` is stored. Correctness is guaranteed by the proof.

### Internal Structure of Stage Circuits

The Process Messages and Process Deactivate circuits are the two most complex circuits. Each one processes a full batch of 3 messages in a single Cairo program. Internally, they are composed of multiple sub-circuit modules, each responsible for an independent cryptographic verification step. The stage program then verifies cross-links between modules to ensure data consistency.

#### Process Messages Stage

Source files:

| File | Role |
| --- | --- |
| `native_process_messages.cairo` | Boundary — batch-level commitment and hash chain constraints |
| `native_process_message_components.cairo` | Sub-components — CoordKey / ECDH / Decrypt / Signature |
| `native_process_message_step_core.cairo` | Step Core — full state transition for one message |
| `native_process_messages_stage.cairo` | Stage entry — composes all modules and verifies cross-links |

#### Process Deactivate Stage

Source files:

| File | Role |
| --- | --- |
| `native_process_deactivate.cairo` | Boundary — batch-level commitment and hash chain constraints |
| `native_process_deactivate_components.cairo` | Sub-components — CoordKey / ECDH / Signature / Decrypt |
| `native_process_deactivate_step_core.cairo` | Step Core — state transition for one deactivation message |
| `native_process_deactivate_stage.cairo` | Stage entry — composes all modules and verifies cross-links |

Key difference from Process Messages: each deactivation message requires **2 ECDH** and **2 Decrypt** operations (because deactivation involves both a command decryption channel and a deactivation leaf encryption channel), and it updates the active tree and deactivate tree rather than the state tree.

```text
┌─────────────────────────────────────────────────────────────────────────────────┐
│                   Process Deactivate Stage (single proof)                         │
```

#### Trees updated by each stage

```text
Process Messages:
  Reads:   state tree (verify stateLeaf exists)
  Reads:   active tree (check voter is not deactivated)
  Updates: state tree (write new pubKey, balance, voteWeight, nonce)
  Unchanged: active tree, deactivate tree

Process Deactivate:
  Reads:   state tree (verify voter's pubKey for signature check)
  Updates: active tree (mark stateIndex as deactivated)
  Updates: deactivate tree (write encrypted deactivation leaf)
  Unchanged: state tree
```

### No Trusted Setup

Unlike zkSNARK (Groth16) systems that require a ceremony to generate proving/verification keys, zkSTARK security relies solely on hash function collision resistance (Poseidon). The compiled Cairo program (Sierra JSON) is the only artifact needed — there is no `zkey`, no "toxic waste", and no trust assumption beyond the hash function.

## Part 2: End-to-End Flow on Starknet

### High-Level Architecture

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                         Off-Chain (Operator)                             │
│                                                                         │
│  1. Collect on-chain events (signups, votes, deactivations)             │
│  2. Compute witness data for each circuit                               │
│  3. Serialize inputs as felt252 arrays                                  │
│  4. Submit (programFile + inputFile) to Atlantic proving service        │
│  5. Atlantic generates STARK proof and registers fact on Starknet       │
│  6. Operator calls round contract to consume the registered fact        │
└─────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                         On-Chain (Starknet)                              │
│                                                                         │
│  MockAmaciRound contract:                                               │
│    • Stores state commitments (state, deactivate, tally)                │
│    • Verifies fact is registered in Integrity FactRegistry              │
│    • Checks public output matches expected commitments                  │
│    • Advances round state upon successful verification                  │
└─────────────────────────────────────────────────────────────────────────┘
```

### Proof Generation Pipeline

```text
┌────────────┐     ┌──────────────┐     ┌───────────────────────────────┐
│ Cairo      │     │ Serialized   │     │         Atlantic              │
│ Source     │     │ Witness      │     │   (Proving-as-a-Service)      │
│ (.cairo)   │     │ (felt252[])  │     │                               │
│            │     │              │     │  1. Execute Cairo program      │
│  scarb     │     │  JS/any      │     │  2. Generate execution trace  │
│  build     │     │  language    │     │  3. Run Stone STARK prover    │
│    ↓       │     │    ↓         │     │  4. Verify proof on Starknet  │
│ Sierra     │────→│ inputFile    │────→│  5. Register fact in          │
│ JSON       │     │              │     │     Integrity FactRegistry    │
│(programFile)     │              │     │                               │
└────────────┘     └──────────────┘     └───────────────────────────────┘
```

The operator submits two files to Atlantic:

| File | Content | Analogy |
| --- | --- | --- |
| `programFile` | Compiled Cairo program (Sierra JSON) | The "circuit" — fixed per parameter set |
| `inputFile` | Serialized witness + public fields (felt252 array) | The "witness" — different each round |

After receiving these two files, Atlantic executes the following pipeline:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Atlantic Internal Pipeline                                 │
│                                                                             │
│  Input: programFile (Sierra JSON) + inputFile (felt252[])                   │
│                                                                             │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 1. Sierra → CASM compilation                                          │  │
│  │    Compiles Sierra JSON to CASM (Cairo Assembly, lowest-level ISA)     │  │
│  │    Also computes program_hash = H(Sierra JSON)                        │  │
│  │    → program_hash lets on-chain contracts verify "proof came from      │  │
│  │      the correct circuit"                                             │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
│                         │                                                    │
│                         ▼                                                    │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 2. Cairo VM execution                                                 │  │
│  │    Runs CASM + inputFile in the Cairo VM                              │  │
│  │    → Produces: execution trace (register state at every step)          │  │
│  │    → Produces: memory snapshot                                        │  │
│  │    → Produces: public output (program return value)                   │  │
│  │    If any assert in the program fails, execution aborts and no        │  │
│  │    proof can be generated                                             │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
│                         │                                                    │
│                         ▼                                                    │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 3. Stone Prover generates STARK proof                                 │  │
│  │    Input: trace + memory + public output                              │  │
│  │    Output: STARK proof                                                │  │
│  │    → Proves "there exists an input that makes the program execute     │  │
│  │      correctly and produce this public output"                        │  │
│  │    → The proof itself contains no private data (zero-knowledge)       │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
│                         │                                                    │
│                         ▼                                                    │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 4. Starknet L2 Proof Verification (9 transactions)                    │  │
│  │    Splits the STARK proof across multiple transactions on Starknet    │  │
│  │    Starknet verifies the mathematical correctness of the proof        │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
│                         │                                                    │
│                         ▼                                                    │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 5. Fact Registration                                                  │  │
│  │    Writes to the Integrity FactRegistry contract:                     │  │
│  │      fact_hash = H(program_hash, H(public_output))                    │  │
│  │    → Anyone can query whether this fact exists                        │  │
│  │    → The AMACI contract queries this fact to confirm proof validity   │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  Final state: fact is registered; Operator can call the AMACI contract      │
│  to consume the fact and advance round state                                │
└─────────────────────────────────────────────────────────────────────────────┘
```

Throughout this process, the Operator's private data (coordPrivKey, etc.) exists only transiently in Atlantic's execution environment and never appears in the proof or anywhere on-chain.

### Round Lifecycle

A complete AMACI round follows this sequence:

```text
  Deploy Round Contract
         │
         │  initial commitments set
         ▼
  ┌─────────────────┐
  │  Add New Key    │  Register voter key, record nullifier
  │                 │  Contract updates: state_commitment, keys_added
  └────────┬────────┘
           │
           ▼
  ┌──────────────────────┐
  │  Process Deactivate  │  Process key deactivation batch (3 messages)
  │                      │  Contract updates: deactivate_commitment
  └────────┬─────────────┘
           │
           ▼
  ┌──────────────────────┐
  │  Process Messages    │  Process vote batch (3 messages)
  │                      │  Contract updates: state_commitment
  └────────┬─────────────┘
           │
           ▼
  ┌─────────────────┐
  │     Tally       │  Compute final vote results
  │                 │  Contract updates: tally_commitment, tally_submitted
  └─────────────────┘
```

Each step produces a proof whose public output contains the **current** and **new** commitment values. The on-chain contract enforces continuity:

```text
contract.stored_commitment == proof.current_commitment  →  accept
contract.stored_commitment = proof.new_commitment       →  advance
```

### Commitment Chain (Integrity Guarantee)

The security of the entire round rests on the commitment chain. Each proof binds a state transition, and the contract ensures transitions are sequential:

```text
                Deactivate                Process Messages              Tally
                ─────────                 ────────────────              ─────
Public Output:  Public Output:            Public Output:
  currentDeactivateCommitment               deactivateCommitment         stateCommitment
  newDeactivateCommitment ─────────────→  (must match)                 (must match)
                                            currentStateCommitment
                                            newStateCommitment ────────→ (must match)
                                                                         currentTallyCommitment
                                                                         newTallyCommitment
```

The contract never replays private computation. It only verifies:

1. The fact hash is registered in the Integrity FactRegistry
2. The program hash matches the allowed circuit for this operation
3. The public output contains the correct AMACI circuit identifier
4. The commitment values link to the contract's current stored state

### On-Chain Contract Role

The `MockAmaciRound` contract maintains minimal state:

```text
Storage:
  state_commitment              Current state tree commitment
  deactivate_commitment         Current deactivation tree commitment
  tally_commitment              Current tally result commitment
  keys_added                    Number of key registrations accepted
  message_batches_processed     Number of vote batches processed
  tally_submitted               Whether final tally has been recorded
  allowed_program_hashes        Allowlist of valid circuit program hashes
  used_key_nullifiers           Set of consumed nullifiers (anti-replay)
```

For each fact submission, the contract:

1. Asserts the caller-provided `current_commitment` matches storage (state continuity)
2. Reconstructs the expected fact hash from the metadata output
3. Queries the Integrity FactRegistry to confirm the fact is registered
4. Verifies the public output header (magic, version, circuit ID, hash scheme)
5. Updates the stored commitment to the `new_commitment` from the proof
6. Emits an event recording the accepted fact

### Cost Structure

The system has three distinct cost layers:

| Layer | What | Who Pays | Example Cost |
| --- | --- | --- | --- |
| Atlantic credits | Proving service fee | Operator (off-chain) | ~$12 per round (4 queries) |
| Proof verification gas | STARK proof verification + fact registration on Starknet | Atlantic (on-chain) | ~17 STRK per round |
| Business wrapper gas | AMACI contract state updates | Operator (on-chain) | ~0.25 STRK per round |

The proof verification cost is dominated by the STARK verification transactions that Atlantic submits to register facts. The AMACI business logic itself (consuming facts and updating commitments) is lightweight.

### Comparison with Groth16-Based AMACI

| Dimension | Groth16 (circom) | zkSTARK (Cairo) |
| --- | --- | --- |
| Trusted setup | Required (Powers of Tau + circuit-specific) | Not required |
| Circuit language | Circom (R1CS constraints) | Cairo (executable programs) |
| Proof generation | Local (rapidsnark) | Cloud service (Atlantic/Stone) |
| On-chain verification | Groth16 verifier contract (~200k gas) | Fact registry lookup (lightweight) |
| Proof size | ~128 bytes | Larger, but verified off-chain by Atlantic |
| Composability | Limited | Native recursive composition possible |

### Summary

AMACI on Starknet replaces the Groth16 proving system with Cairo programs and STARK proofs. The core protocol logic — encrypted votes, coordinator-mediated processing, commitment-chain state machine — remains identical. The key advantages are:

- **No trusted setup**: security relies only on hash function collision resistance
- **Transparent verification**: anyone can verify the Cairo program source and the registered facts
- **Proving-as-a-Service**: operators submit program + input to Atlantic; no local prover infrastructure required
- **On-chain efficiency**: the Starknet contract only checks fact registration and commitment continuity, keeping gas costs minimal for the business logic layer
